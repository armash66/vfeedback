# Authentication & Sign-In

VFeedback authenticates users using [VAuth](https://accounts.vosslabs.org), the unified OpenID Connect / OAuth 2.1 identity provider for VOSS products.

**There are two questions, answered in different places:**

1. **Who is this person?** VAuth answers this. It verifies their college email mailbox (`@vit.edu.in` or `@vosslabs.org`).
2. **What can they do here?** VFeedback answers this from its own database. VAuth only answers who the person is and has no roles. Any verified VAuth account is a regular signed-in user. Staff and department roles will come later from our own database records.

---

## How Sign-In Works

1. A user navigates to `/login` and clicks **Sign in with VOSS**.
2. Better Auth starts an Authorization Code flow with **S256 PKCE** and scopes `openid profile email` targeting VAuth's authorization endpoint (`https://accounts.vosslabs.org/api/auth/oauth2/authorize`).
3. After the user authenticates at VAuth with their one-time passcode, VAuth redirects to `/api/auth/oauth2/callback/voss`.
4. Better Auth exchanges the authorization code using `client_secret_post` with the S256 code verifier and validates the issuer (`requireIssuerValidation: true`).
5. `mapProfileToUser` validates that `email` is present and `email_verified` is true. If the provider profile does not supply a name, a name is derived from the title-cased local part of the email. VAuth enforces the email domain, so relying parties do not re-check it.
6. Better Auth sets an HTTP-only, signed session cookie for VFeedback that lasts 7 days (updated daily).
7. `requireUser(request)` validates the session (or active dev persona) and redirects signed-out users to `/login?next=<safe path>`.
8. Sign-out via `POST /logout` validates the CSRF Origin host against `APP_URL`, terminates the Better Auth session, clears dev persona cookies, and redirects to `/`.

## Environment Configuration

| Variable             | Description                                                                                                                  | Example / Default                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `BETTER_AUTH_URL`    | The public origin of this application. Matches `APP_URL`.                                                                    | `http://localhost:5173`                                                   |
| `BETTER_AUTH_SECRET` | 32-byte secret generated by `npm run setup` to sign session cookies and dev persona tokens. Independent of `SESSION_SECRET`. | `<generated-32-byte-hex>`                                                 |
| `VOSS_DISCOVERY_URL` | Canonical OIDC discovery document URL. Must match canonical value.                                                           | `https://accounts.vosslabs.org/api/auth/.well-known/openid-configuration` |
| `VOSS_CLIENT_ID`     | OAuth 2.1 client identifier issued by a VAuth maintainer.                                                                    | `<issued-client-id>`                                                      |
| `VOSS_CLIENT_SECRET` | OAuth 2.1 client secret issued by a VAuth maintainer.                                                                        | `<issued-client-secret>`                                                  |
| `VFEEDBACK_DEV_AUTH` | Set to `"1"` to enable local dev personas. Must be empty or unset in production.                                             | `"1"` (dev only)                                                          |

When `VOSS_CLIENT_ID`, `VOSS_CLIENT_SECRET`, or `VOSS_DISCOVERY_URL` are missing or non-canonical, the sign-in button is disabled with a clear notice that sign-in is not configured, and handshake/callback requests fail safely without exposing internal details.

## Local Development with Personas

Contributors who do not possess production VAuth client credentials can test signed-in user functionality using local development personas.

- **Enable**: Set `VFEEDBACK_DEV_AUTH=1` in `.env` (development / test only).
- **Production Guard**: If `NODE_ENV === "production"` and `VFEEDBACK_DEV_AUTH === "1"`, application startup and `npm run build` will immediately throw a fatal error.
- **Cookie Security**: The selected persona is stored in an HTTP-only cookie signed with HMAC-SHA256 using `BETTER_AUTH_SECRET`.
- **Identity Only**: Dev personas substitute identity fields only (`userId`, `email`, `name`). A cookie check never decides who someone is.

### Available Personas

| Key         | Name      | Email                    | Role / Description                    |
| ----------- | --------- | ------------------------ | ------------------------------------- |
| `student-a` | Student A | `student.a@example.test` | Enrolled student identity (Persona A) |
| `student-b` | Student B | `student.b@example.test` | Enrolled student identity (Persona B) |

The seed script (`npm run db:seed`) automatically creates `user` rows for these development personas in development and test environments.

## VAuth Client Registration

To register VFeedback with the central VAuth provider, a maintainer adds this entry to `clients.config.ts` in the `vauth` repository:

```ts
{
  name: "vfeedback",
  description: "Campus facilities and lab feedback platform.",
  redirectUris: [
    "http://localhost:5173/api/auth/oauth2/callback/voss",
    "https://feedback.vit.edu.in/api/auth/oauth2/callback/voss", // TO CONFIRM: production redirect URI
  ],
  scopes: ["openid", "profile", "email"],
  firstParty: true,
},
```

Maintainers run `npm run clients` in VAuth to generate `VOSS_CLIENT_ID` and `VOSS_CLIENT_SECRET`, which are securely provided to the VFeedback deployment environment.

## Troubleshooting

| Symptom                         | Cause                                                                                      | Solution                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `INVALID_OAUTH_CONFIGURATION`   | `VOSS_*` env vars are missing or empty where the app runs.                                 | Ensure `VOSS_DISCOVERY_URL`, `VOSS_CLIENT_ID`, and `VOSS_CLIENT_SECRET` are set.   |
| Sign-in fails at token endpoint | `pkce` is not set to `true`.                                                               | Verify `pkce: true` in genericOAuth configuration.                                 |
| VAuth rejects redirect URI      | Registered URI does not match current request URL (scheme, host, port, or path).           | Ensure exact match with registered URI in `clients.config.ts`.                     |
| `name_is_missing`               | No `mapProfileToUser` fallback while `user.name` is `NOT NULL`.                            | Handled by `mapProfileToUser` deriving name from email if missing.                 |
| `account_not_linked`            | Local account with same email already exists and auto-linking is disallowed or unverified. | `trustedProviders: ["voss"]` and `requireLocalEmailVerified: true` are configured. |
| Token exchange rejects client   | Incorrect client secret or rotated secret.                                                 | Request current secret from a VAuth maintainer.                                    |

## Operations

### Cookie Cache Tradeoff

Better Auth's session cookie cache is enabled (`session.cookieCache: { enabled: true, maxAge: 300 }`) to minimize database overhead on high-traffic pages. When enabled, valid session data is cached client-side in a signed cookie for up to 300 seconds (5 minutes). The operational tradeoff is that a revoked session or session data change may take up to 5 minutes before the revoked session stops working, unless explicitly signed out or invalidated on the client.

### Rotating Secrets

`BETTER_AUTH_SECRET` is used to sign and verify session tokens and dev persona authentication cookies. Rotating this secret immediately invalidates all active sessions and signs everyone out across the application. Each deployment environment (development, staging, and production) must have its own unique, securely generated 32-byte secret. Never share secrets across environments.

### Session Privacy & Telemetry

In accordance with college privacy constraints, user sessions store no client IP address or user agent. `advanced.ipAddress.disableIpTracking` is set to `true`, and a `databaseHooks.session.create.before` hook explicitly overrides `ipAddress` and `userAgent` to `null` before session rows are inserted into the database. The database columns are retained in the schema for compatibility with the Better Auth Drizzle adapter.

### 7-Day Sliding Session Lifetime

Sessions utilize a sliding window model:

- **Total Expiry (`expiresIn`)**: 7 days (604,800 seconds).
- **Update Frequency (`updateAge`)**: 1 day (86,400 seconds).
  Active users who interact with the application at least once within 7 days have their session expiration slid forward by 7 days once daily, avoiding unexpected sign-outs while naturally expiring dormant sessions.

### Staging Redirect URIs

VAuth strictly enforces redirect URI allowlisting. Any staging or preview environment must have its exact redirect URI (e.g. `https://feedback-staging.vit.edu.in/api/auth/oauth2/callback/voss`) registered in advance in VAuth's `clients.config.ts` before deployment. Unregistered domains or mismatched schemes/ports will result in rejection at the authorization endpoint.
